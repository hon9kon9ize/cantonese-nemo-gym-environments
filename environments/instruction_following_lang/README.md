# instruction_following_lang

Multilingual (yue / zh-hk / en) IFEval-style **verifiable instruction following**,
forked from the base `instruction_following` env with the shared multiplicative
language penalty + format gate (same recipe as `code_gen_lang`,
`math_with_judge_lang`, `stem_mcqa`):

```
reward = if_reward * language_multiplier * format_factor
```

- **`if_reward`** — the fraction of the appended verifiable constraints the ANSWER
  satisfies (`grading_mode: fraction`, denser GRPO signal; `binary` = all-or-nothing).
  The answer is the text AFTER `</think>`; the language check reads only the
  reasoning BEFORE it.
- **`language_multiplier`** — enforces the per-row reasoning language and forbids
  Simplified Chinese (`nemo_gym.language_penalty`, `wrong_lang_floor=0.1`,
  `min_target_script_ratio=0.15` for code-mixing tolerance).
- **`format_factor`** — closed `</think>` required, else `floor=0.2`.

## Dual verifier registry (the key difference vs the base env)

The yue / zh-hk rows were generated by a sibling **`nemo-instruction-following`**
project, NOT translated — a rule-based Cantonese / Written-Chinese design layer. Its 52
CJK-aware verifiers (`chinese:*`, `cantonese:*`, plus jieba/CJK-reimplemented
`length_constraints:*` / `count:*` / `punctuation:*`) are **vendored** here under
`cantonese_rlvr/` (`registry.REG`). NVIDIA's upstream `verifiable_instructions`
package does **not** have them.

The `en` rows come from the original English IFEval blend and use **9 English-only
letter/case types** (`change_case:*`, `letters:letter_counting{,2}`,
`keywords:{palindrome,letter_frequency,no_adjacent_consecutive}`,
`count:lowercase_counting`, `change_case:capital_word_frequency`) that the
Cantonese project deliberately **dropped**. Those are graded by NVIDIA's
`verifiable_instructions`.

So `verify()` **routes by row `language`**: `en` → NVIDIA primary (its kwargs were
authored for that grader), yue/zh-hk → REG primary; each falls back to the other
for any id the primary doesn't know. A constraint no registry can grade (or a
non-deterministic one returning `None`, e.g. jyutping rhyme without pycantonese)
is excluded from the denominator — matching the infinite-rl `nemo_reward._if_reward`
reference.

`verifiable_instructions` (+ its spaCy/nltk deps) is **optional**: the app guards
the import, so if the venv can't fetch it the env still runs — `en` rows just lose
those 9 constraints. Coverage on this cluster's data: yue/zh-hk 100% via REG; en
needs NVIDIA for full coverage (12 en rows are English-only, 262 partially).

## Dependencies

`cantonese_rlvr/` vendors its own `jieba` + `toml` under `_vendor/` (on `sys.path`
via its `__init__`); `jsonschema` / `pyyaml` are already in the container.
`requirements.txt` adds only NVIDIA's `verifiable-instructions` + the spaCy English
model for the `en` path. `nltk` `punkt_tab` is pre-fetched to `~/nltk_data` during
`prebuild_gym_server_venvs.sh` (home is network-mounted → visible on compute nodes).

## Data

`prepare_instruction_following_lang_data.py` (workspace root) builds
`data/{train,validation,smoke}.jsonl` from
`nano_v3_sft_profiled_instruction_following.jsonl`. **No `pass_rate` filter** — the
`pass_rate` field in that file is a PLACEHOLDER (the dataset hasn't been profiled
with our model yet). It only retargets `agent_ref` and stratifies by language.

## Benchmark

`benchmark/benchmark_instruction_following_lang_job.sh` profiles a deployed vLLM
policy against the exact `verify()` GRPO will optimize (per-language pass rate,
if_reward, language / format multipliers, constraint coverage), and verifies the
dual-registry wiring end-to-end.
